# Contracts: New Project

## Routing and screen

- `/projects/new` is a static authenticated route inside AppLayout, before `/projects/:id`.
- Projects New project/empty-state actions navigate to it. `/projects/:id/edit` uses the same form sections with an existing-project lifecycle; every Edit entry point navigates there and the old inline editor is removed. Bulk actions remain functional.
- Heading, label grid, type cards, tasks/team, invoice defaults and persistent footer match the handoff; no DevBar or second sidebar.
- Form controls have visible labels and stable IDs. Optional dates support clearing; tags use Enter/comma/remove and cannot trigger form submission.
- Planning dates display `DD Mon YYYY` while preserving ISO dates in the draft. Their 180px fields use `--width-planning-date`, existing form utilities and the shared day-mode `DatePicker`; clearing restores the labelled field's focus. Only the New Project wrapper opts into top-layer placement and calendar focus handling. Reopening resets the browsed month to the selected date; Escape restores the trigger and Tab can leave without trapping focus. Timesheet/gallery calendar defaults are unchanged. Runtime viewport positioning reuses the existing popover script, not inline visual styling in RSX.
- Client and currency use `SelectField` over the shared form/menu primitives. Client search stays inside the panel and uses the existing authorized catalog resource, with pending/empty/error states and disabled archived or unavailable selections. Searching never changes the selected client. An explicit currency survives client changes; the empty currency value means client inheritance. `--width-form-select` maps the handoff's 320px width/basis without changing the compact Projects/Gallery filters. Arrow keys, Home/End, typeahead, selection, Escape and focus restoration operate on enabled choices; search input retains native editing and composition keys. Native popover geometry follows changing result heights, including upward placement in short viewports.
- Code uses the 160px `--width-project-code` token and an adjacent real previous-code/suggestion; a suggestion is not applied automatically. Tags reuse `.chip-input` with the opt-in neutral chip variant, `--width-tag-entry` (140px) and `--height-form-control` (44px). Enter/comma adds a trimmed, case-insensitive distinct batch, empty Backspace removes the last chip, and a labelled remove button returns focus to the field. Overlong or over-capacity batches retain the pending input and show an error instead of dropping text. Composing text is not submitted by Enter. Shared chip-input defaults remain unchanged; downstream tag filtering is tracked separately under T015.
- Cancel/back retains an acknowledged draft; explicit Discard draft confirms deletion. Save project is disabled with missing required fields or pending commit.
- Use explicit loading/error/empty states, preserve unsaved input, announce errors/save status and restore modal focus.

New error handling distinguishes bad input (400), unauthorized (401), forbidden (403), missing/foreign resource (404) and revision/state conflict (409). Foreign draft IDs do not disclose ownership. Unexpected failures log sanitized context and return a safe message.

Basic and invoice-default validation rejections include a typed `details.field` identity (`client`, `name`, `code`, `starts_on`, `ends_on`, `currency`, `admin_notes`, `payment_terms`, `purchase_order`, `tax`, `second_tax_name`, `second_tax` or `discount`), without echoing the submitted value. An inverted planning range targets the end date. The screen accepts recognized field identities on 400 responses, links the control to its visible error and focuses it after unlocking the form. The only additional correctable status/field pairs are 404 with `client`, `task` or `person`, and 409 with `task_name` for an archived catalog-name conflict. Retry clears the prior field rejection without discarding input or automatically repeating a definitely rejected finalization. Unknown/transport/revision-conflict errors retain the general recovery path. The remaining whole-form acceptance matrix is tracked under T046/T048; this contract is not a claim of whole-form completion.

After a definite typed field rejection, Save explicitly resubmits the latest corrected values; Cancel/back preserves the incomplete draft and Discard still requires confirmation. These actions clear the old field error before entering the existing serialized intent path. An uncertain save or finalization has no typed field identity and still requires its original Retry path; it cannot be replaced with an unrelated action or a fresh creation request.

Billing rejections also identify `project_type`, `rate_mode`, `project_rate`, `budget_mode`, `budget_value`, `budget_alert`, `budget_alert_at`, `fee_amount` and `milestones`. Missing milestones target the Add milestone control. Row-specific errors encode `details.field` as an object with one typed key (`milestone_name`, `milestone_date` or `milestone_amount`) and the row UUID; labels and list indices are not identities. Malformed UUIDs are not accepted as focus targets. A milestone total overflow identifies the amount that exceeds the supported range. Invalid hidden billing values remain in the draft but do not block another active project type/mode. If email configuration becomes unavailable, the error targets the still-editable email checkbox so the creator can disable it, not the disabled percentage field. Duplicate IDs and draft size limits retain the general rejection path.

Assignment errors use the same typed object: `task`, `task_name`, `task_access`, `task_rate` and `task_budget` carry the draft task-row UUID (not its catalog task ID); `person`, `person_rate`, `cost_rate` and `person_budget` carry the teammate's user UUID. A per-task budget total overflow identifies the row whose addition exceeds the supported range. Invalid new-task names focus the row's removal control with instructions to re-add a corrected name; invalid access focuses its existing access dialog trigger. An unavailable task/person focuses its removal control; an unavailable client focuses the existing selector. Removing a row returns focus to task entry or teammate selection, while closing the access dialog returns it to the trigger. Field links and messages are local to that row; other values remain intact. Resuming a draft retains unavailable selections until explicitly corrected. This does not change active-mode validation, rate inheritance, cost authorization, HTTP status codes or the draft schema.

## Draft concurrency

Existing-project editing is separate: it never autosaves operational settings. Save changes is explicit; Cancel/back/navigation with dirty input offers staying or discarding changes. A failed validation or transport request retains entered values. Reload-latest requires acknowledging the loss of local changes. Project editing neither resumes nor discards a creation draft.

Save requests serialize per page and carry the last acknowledged server revision. Edits during an in-flight save remain dirty and are coalesced into the next request. Acknowledging an older snapshot never marks newer input saved. Finalization prevents new autosave work and submits the latest snapshot after any pending save finishes. Server checks remain authoritative if clients bypass the UI.

Two-tab conflict provides reload-latest without silently discarding local input. Creation uses the shared editor navigation guard from the first dirty value through debounce, outstanding writes and uncertain responses. Same-document links and programmatic history changes are blocked until acknowledgement or recovery; rejected Back/Forward restores the original entry without unmounting the form or adding history entries. Reload and full-document exits use the browser's native confirmation, which can explicitly accept losing unacknowledged local input. Cancel/back serializes a final save before leaving; confirmed discard and successful creation explicitly release the guard. Acknowledged drafts remain resumable. No fake timestamps or unconditional success toast.

Personal timesheets remain readable by their owner. Project settings do not expose another user's time-entry details. Own running timer stop is safe after restriction revocation; starting/editing restricted work is refused. Historical archived-context edits keep existing permissions. Privileged approvals/imports retain their existing authority.

Project list, spend and team reads use `project_read_access` with the actor's current active database role and organization, not a role cached in a caller DTO. Missing settings preserve assigned legacy-member progress. Project leads/admins receive assigned progress without financial rates; an ordinary assigned member needs `project_members` visibility. Historical own entries grant identity lookup only, never team or progress access.

Saved basic details and project-tag links use the same progress boundary. Details return the persisted name/code, client name, currency, planning dates and ordered tags; notes are included only for the current database administrator role and omitted from other serialized responses. Inaccessible details return not-found. Tag filtering uses tag UUIDs, never display-name equality, and includes only links to authorized projects; orphan labels and private-project-only labels do not appear. Changing the Projects tag filter clears bulk selection, combines with the existing search/client/status filters, and Reset filters clears it. Failed or pending tag reads cannot silently turn a selected tag into an unfiltered list. These read/filter operations never delete a shared label.

Reports reuse the authorized tag catalog, including archived project history. Optional `tag_id` intersects the existing date/client/project/person filters in grouped and detailed queries and CSV/XLSX downloads. Matching uses an organization-scoped existence predicate, so multiple project tags never multiply entries or amounts; unknown or foreign tag IDs match no rows. XLSX applies the filter before size limits in the same snapshot as the payload. Missing `tag_id` retains the existing unfiltered behavior. Report tables hide stale results while a changed filter is pending or failed and offer an explicit retry; export links carry the selected tag UUID.

Timesheet and Timer use separate rate-free `list_tracking_projects`/`list_tracking_tasks` resources. They retain archived identities from the viewer's own history; the ordinary task catalog remains active-only. Unauthorized optional rates/budgets are absent in serialized responses and remain deserializable as absent values. Tracking identities are not a grant to start/edit work: the existing context and mutation guards stay authoritative.

Count, pagination, export and detail queries use the same authorization projection. Do not add private fields to plugin payloads/granted tables. Existing organization-report manager gate remains.

Project CSV and XLSX exports require `can_view_progress` just like Projects. XLSX size/count checks apply that filter before limits and share their existing read-only repeatable-read transaction with the payload query. Harvest project counts, pages and detail use the same view; unavailable detail is 404. Own time-entry project identities remain readable without granting project-wide budget access.

UI task reads and Harvest task counts/pages/detail share `task_read_access`: active organization managers/admins see the catalog; members see assigned-project tasks and their own historical task identities. Task identity does not grant tracking access. Member task rates are omitted. Harvest time-entry queries revalidate the current active actor, even if the supplied role is stale. Entries omit `budgeted` without progress access, omit member financial rates, and expose project cost overrides only to administrators. Managers retain legacy profile costs only when no project override exists; an inaccessible override is not replaced with a fabricated fallback.

Grouped reports resolve organization and manager/admin authority from the current active viewer ID. A manager's group containing any project cost override omits `cost_cents` altogether; it does not expose the override, substitute a profile rate or return a partial cost. Other groups retain their legacy costs, while administrators see exact effective totals. The UI labels missing group/grand-total costs `Restricted`; billing amounts and worked hours remain available. Detailed time CSV/XLSX exports contain no cost fields.

## Billing and downstream invariants

Client default amounts belong to the client's currency, including zero. The existing client editor locks the row and rejects a different currency when a default rate exists, because that request contains no replacement amount. Rejection changes no fields and retains the form input. Equivalent case/whitespace preserves the stored currency; other details remain editable and idempotent. Clients without a default rate retain legacy currency editing. The check uses the latest locked row, including a concurrently added default rate.

Missing settings preserves all legacy rates/amounts. New selected modes have parity across Rust/SQL, project spend, reports, invoice preparation and compatibility exports. Zero is not absent; currency mismatch is not conversion.

Catalog task amounts carry an optional source currency rather than assuming the workspace denomination. A configured task-billed project can inherit a non-null amount only when its known currency matches the project; unknown/incompatible currencies require an explicit amount, including zero. Named-task reuse applies the same rule as UUID selection. Creation errors identify the task row and preserve the draft; UI placeholders show only compatible defaults and otherwise request a rate. A null catalog amount still allows the existing client fallback. Existing project-task snapshots and legacy inheritance remain unchanged; neither migrations nor import retries guess or overwrite historical currencies.

The existing project editor rechecks settings after locking the project. For configured projects it preserves the type and currency: changing either requires an atomic replacement of the associated billing configuration/amounts, which this editor does not supply. Case/whitespace-only currency input preserves the canonical stored value. Project-rate mode requires an explicit rate, including zero; other modes cannot accept an unused project-rate change. Task/person budget units and aggregate values cannot be changed independently of their allocations. Project-wide budgets remain editable within the creation type's allowed denominations. Compatible names/rates/totals retain ordinary edit and no-op semantics; rejection writes nothing. Missing settings retain legacy editing. The existing shared fields display these capabilities with explanatory hints and omit unsupported monetary-budget choices. Pending saves disable inputs, Save, Cancel and switching to another project's editor; errors retain values for retry. This does not add a configuration migration or redesign Project Detail.

Imports must not relabel a source task rate as the currency of a configured project. When inserting a new project-task link with an explicit source rate, compare its trimmed currency case-insensitively with the project currency; use the organization default only when the source currency is absent or blank. A mismatch rejects that row and rolls back its parent/link changes without contaminating subsequent lookup state. Existing links retain their stored overrides and do not consume incoming rates. Projects without settings retain legacy import behavior. This import-link boundary is separate from the catalog denomination rules above.

Configured fixed fees use fee occurrences, not synthetic time. Non-billable projects never supply invoice lines. Monthly budgets use the selected month; lifetime tracked totals remain available separately. Per-task/person budgets are keyed to real selected entities.

Projects uses the same configured consumption evaluator as budget alerts. The overview selects the current UTC month and identifies it explicitly; lifetime tracked hours are shown separately. Task/person scopes have a keyboard-accessible native disclosure below the project identity so a combined allowance cannot hide an individual overrun. This disclosure extends the handoff's three existing budget columns without changing their grid or shared component styles. Negative remaining hours/amounts retain their sign; display percentages use integer arithmetic. An unallocated budget is absent, not zero, and partial/overflowed allowances are not presented as a complete total. Loading or failed progress never falls back to lifetime figures. Projects without settings keep their lifetime overview and existing plugin alert path.

Invoice defaults are snapshots, editable on drafts; conflicting defaults require explicit resolution. CSV/XLSX/PDF and displayed totals include every adjustment component and identify currency. A new project does not issue invoices or send client email.

`prepare_invoice` is manager-authorized and accepts the same client, inclusive period, optional project selection and optional invoice overrides as generation. It returns project-specific defaults, time/fee preview lines with currencies, a checked subtotal and optional resolved defaults/adjustments/due date. Mixed defaults leave those optional fields absent until explicitly resolved; selected projects without eligible work still participate. A repeatable-read, read-only PostgreSQL transaction keeps all inputs in one snapshot and prevents materializing or claiming fees. Preview and generation share time eligibility/rate calculations and fee calendars; existing occurrence identities win over changed schedules, including claimed or released occurrences. Preview rejects more than 10,000 time rows or 1,000 contributing/selected projects rather than truncating; fee limits remain 10,000 occurrences and 1,200 months per project. This is an estimate, not a reservation: generation revalidates current sources and claims them transactionally.

Invoice presentation reads the saved subtotal, discount, individual taxes and total without recalculating project defaults. Nonzero discount/first-tax rates and any configured second tax appear as separate labeled rows; discounts are negative display amounts. Payment terms, due date and purchase order belong to the invoice. CSV/XLSX retain Description/Hours/Rate/Amount as their first four columns and append Currency/Issued on/Due on/Payment terms (days)/Purchase order on every row. Fixed fees retain absent hours and hourly rates. XLSX stores normal amounts as numeric cells and amounts exceeding Excel's 15-significant-digit precision as exact decimal text. PDF preserves the organization's free-text terms alongside the invoice's own payment period. Export preflight includes purchase-order and second-tax-name text in its existing size checks.

Generation accepts an optional bounded selection of project IDs and explicit invoice overrides. Empty selections, unavailable/cross-client/foreign projects and invalid percentages/text/terms are rejected; duplicate selected IDs collapse without duplicate charges. Time and fee queries use the same selection, including already-materialized unclaimed fees. Without a selection, contributing projects determine defaults; an explicit selection also includes selected projects without currently eligible work when resolving defaults. Missing project configuration means Net 30 and zero adjustments. Differing defaults return a conflict unless explicit invoice values are supplied. Generation and draft-only default edits reuse core arithmetic and preserve project source amounts. Editing payment/tax/discount defaults alone does not rewrite invoice lines; explicit fixed-fee line edits follow FR-024. The edit locks the invoice before checking its state so a concurrent send cannot accept a late edit. Voiding retains invoice-owned values and historical lines.

Invoice preparation first reviews sources and prefills compatible defaults. Mixed defaults require explicit input or choosing one project's defaults before reviewing again. Changing client, period, selected projects or invoice values invalidates the visible estimate and disables generation until reviewed. Pending requests disable the local inputs and Cancel action; errors retain entered values. Generation sends the reviewed project selection and explicit defaults, then opens the saved draft. This is an estimate, not a source reservation: generation rechecks available work. Draft-only edits share the payment/PO/tax/discount controls, disable competing status changes and preserve project defaults and source amounts. Fee rows show absent hours/rates rather than invented time.

The 2026-09-23 clarifications (FR-024/025) require editable invoice-owned fixed-fee amounts/descriptions, partial billing, agreed/invoiced/remaining context and explicitly confirmed overbilling with a signed, labelled negative balance. Source preservation means leaving the project's agreed fee and other invoices intact, not locking every draft line to the full occurrence amount. Migration 0040 supersedes exclusive claims with discounted contributions; the checkpoint below distinguishes that implemented foundation from the remaining editing/confirmation flow. A discount reduces consumption rather than waiving the remainder. Default edits replace the contribution atomically, and void releases only that invoice while retaining its snapshot. Time-entry eligibility remains unchanged. T043 stays open until editable amounts/descriptions, current-balance confirmation and project context are integrated and verified.

## Partial fee request contract (FR-024/025)

**Reviewed generation checkpoint**: `prepare_invoice` now accepts optional complete fee selections (stable source, invoice-owned description/amount and selected state). It validates these without writes and computes totals/contributions only for selected rows; time sources remain non-editable. `generate_invoice` now requires an `InvoiceGenerationRequest` in place of the bare request ID: UUID v7, complete reviewed preparation and exact source/excess confirmations. Under the organization invoice lock it rechecks the active actor, current sources, agreed/invoiced balances, explicit defaults, dates, currency and calculated amounts before saving. Requests are canonically ordered and bounded to 256 KiB. A changed snapshot or missing/extraneous excess confirmation rejects atomically; only selected planned fees are materialized. An identical committed replay returns the original invoice without redispatching creation. The browser carries the complete reviewed request, retains it for uncertain retries and discards it when explicitly reviewing again. Initial fee-edit controls and fully consumed/over-invoiced source discovery remain pending; this endpoint checkpoint does not claim the whole preparation UI is editable yet.

**Stable preview checkpoint**: each preparation line carries `InvoiceSource::Time { entry_id }` or `InvoiceSource::Fee { project_id, period_key }`. Fee lines include agreed, non-void invoiced (including drafts), and signed remaining amounts before the proposed invoice. Resolved defaults also supply each line's proposed net before tax; unresolved defaults leave it absent, not zero. Discount ties use source order rather than the displayed dates, matching persisted allocation. The UI displays this context without changing table columns or shared styles. Preparation remains read-only and keeps the existing available-source filter; editable selection, settled-source overbilling and transactional comparison with the reviewed result are not implemented by this checkpoint.

**Implemented balance checkpoint**: generation requires a caller-stable UUID v7 `request_id`, bound to the authenticated organization/actor and canonical client/period/project/default values. A committed replay returns the original invoice identity and never re-emits creation, even after voiding. The browser's uncertain-response path retries that same payload without another review or a second invoice. Migration 0040 replaces exclusive fee claims with net pretax contributions; discounted balances are available to subsequent preparation, draft edits replace contributions, and void excludes only that invoice. Existing-draft edits now support reviewed excess confirmation as described below; initial generation still rejects excess and does not expose editable source rows.

**Draft editor checkpoint**: `get_invoice_editor` returns current draft revision, invoice defaults, editable existing fee lines, currency and per-occurrence balances. `review_invoice_edit` accepts that revision/defaults/complete fee selection and returns exact totals, net contributions and signed remaining/excess amounts without writes. `save_invoice_draft` accepts a UUID v7 request identity, the reviewed edit/result and exact `(line_id, excess_cents)` confirmations; it rechecks everything transactionally. Unknown/duplicate/missing fee lines, invalid descriptions/amounts, stale revisions/balances and unconfirmed excess reject without writes. Existing zero-valued fees may remain zero; a positive existing charge cannot be silently dropped by entering zero. The former public `update_invoice_defaults` mutation is removed, so it cannot bypass revision/review checks. Its test adapter delegates to the new production workflow.

The existing invoice form now loads this editor explicitly, preserves raw amounts/descriptions on rejection, invalidates review after changes, and requires a labelled native confirmation dialog for an exact excess. Escape/Cancel write nothing. A lost save response locks inputs/Cancel and retries the identical request; stale-tab errors preserve local fields. Controls and dialog reuse existing components/utilities with no shared CSS changes. There is no invoice-screen prototype in this handoff: this is a functional extension of the existing invoice form, not a claim of matching an absent design surface. Editable generation previews, project balance display and invoice navigation/reload recovery remain separate unfinished work.

Target behavior supersedes the exclusive claim description above; completion remains tracked in T061–T068. Preparation exposes stable time-entry identities and fee `(project_id, period_key)` keys without creating database rows. Fee context includes agreed amount, consumed amount including draft reservations, signed remaining balance, proposed gross and proposed net contribution. Draft editing excludes that draft's old contribution when computing availability for its replacement.

Fee edits accept an invoice-owned nonempty description (at most 1,000 characters, no NUL) and nonnegative exact minor-unit amount. Zero means no charge from an unselected preparation row; a selected charge must be positive. A 100% discount may produce a zero net contribution. Time quantities/rates and project schedules are not editable through this contract. Negative balances say "Over-invoiced" and retain their sign.

Generation and draft editing carry a UUID v7 request identity, the reviewed source selection/balances, explicit invoice defaults and exact excess confirmations. Changing client, period, selection, line amount or discount invalidates review and confirmation. Any balance change detected at save returns a conflict without writes; a new review is required. Identical retries reuse the request identity and payload, while changed input requires a fresh identity. Draft edits additionally compare the current invoice revision; sent/paid/void invoices cannot be edited. Confirmations apply to net pretax amounts, including a discount-only edit that increases consumption. A retry never redispatches invoice creation.

All amounts and adjustments are calculated server-side using the pure core allocation helper. The sum of line contributions is exactly subtotal minus discount; taxes never consume fee balances. Preparation and authorized project context use the same balance definition. Member financial privacy and existing time-source eligibility remain unchanged.

## Optional email deployment

Administrator configuration supplies absolute sendmail-compatible executable and sender; no shell command text. Availability is returned truthfully to the UI. Reject header/recipient injection, bound subprocess time/output, use direct stdin message and fixed arguments. Tests use an isolated stub, never the user's mail configuration.

Outbox claims are event-kind scoped and lease-fenced. Logical uniqueness prevents repeated enqueue for the same project/scope/period/threshold/recipient. Message-ID remains stable; retries after unacknowledged acceptance may duplicate receipt. Permanent failure is observable and never displayed as sent.
